# Lark live acceptance — 15 September 2026

Candidate: `main` at `80b94a25` (published as **1.8.5b10**). Run against a
dedicated Lark application created by the fixed `co auth lark` flow, in a group
created for this run. The inbox was isolated with
`CO_INBOX_HOME`, so the owner's real `~/.co/inbox/lark` was untouched. All
messages were synthetic markers. Times are UTC.

> **Gate 3 passed on a second attempt later the same day.** The first attempt is
> kept below unedited, because *why* it failed is the finding: the bot could not
> read group history, so the recovery path had never once run. Granting that one
> scope — through a link, not a console visit — made it pass with recovery as the
> proven mechanism. See **Gate 3, re-run** at the end.

## Setup

- Application `cli_aa221ce7eaf8de14`, bot activated, events delivered over a
  persistent connection with `im.message.receive_v1` subscribed.
- Group created via `lark-cli im +chat-create --bots …`; membership confirmed as
  one user and one bot.
- Listener: `co lark listen` in the foreground, connected `02:59:11`.

## Passed

**Gate 1 — real channel.** A user @-mention was posted at `12:59:26` (provider
create_time). The queue file appeared at `12:59:27` — about one second. The log
recorded `received om_…dfdf90`, and the message carried `mentioned=true`.

**Gate 2 — atomic take.** Two `co lark receive --no-start -t 0` processes raced
for that one message. One exited 0 with the JSON; the other exited 124 with
nothing. `reply` then returned a distinct real message id, read back
independently through `lark-cli`.

**Gate 4 — CLI contract.** `co lark --help` lists all nine verbs: listen,
receive, send, reply, done, check, ls, log, consume. `check` reported the
recovery failure below in its own words, named the details file, and **exited 1**
so a script can detect it.

**Gate 5 — no credentials in tests.** `tests/conftest.py` gives every
non-`real_api` test a fresh temporary `HOME` (`_never_touch_the_real_home`) and
fails any default-run test that opens a non-loopback socket (`_no_network`). The
live procedure is this document, not a pytest marker. Full offline suite:
**9,441 passed**, with only the four known cross-test-pollution failures, each of
which passes in isolation.

## Gate 3 — no message lost or duplicated across a gap

Two gaps were run. In both, the during-gap message arrived **exactly once**.

| | restart variant | freeze variant |
|---|---|---|
| method | listener killed and restarted | `SIGSTOP` / `SIGCONT` on the listener |
| gap | `03:00:30` → `03:00:52` (22 s) | `03:04:18` → `03:06:59` (161 s) |
| during-gap message | `om_…590353`, sent `03:00:40` | `om_…be7b2`, sent `03:04:59` |
| arrived | `03:00:56`, 4 s after reconnect | `03:06:59`, on resume |
| copies in `received.jsonl` | 1 | 1 |

The freeze variant additionally produced a **real duplicate**: the same message
was delivered twice within the same second and the second was refused —
`duplicate om_…be7b2 dropped` — before reaching `received.jsonl` or `new/`.
Nothing was lost and nothing was duplicated, which is what the gate asks for.

## What this run does not establish

**The gate is not closed.** Two reasons, both of which matter more than the table
above.

**1. Neither gap reproduced the 8 September fault.** That run aborted the
established WebSocket transport and *rejected the SDK's reconnect attempts* for
135 seconds, forcing the server to decide whether to redeliver. `SIGSTOP` does
not do that: it freezes the process while the kernel socket buffer keeps
accepting. The log shows the order plainly — the gap message was received at
`03:06:59`, and only *then* did the client log `reconnecting`. The message came
out of a local buffer, not from server-side redelivery after a dropped
connection. Longer than the heartbeat is not the same as disconnected.

The owner capped fault injection at these two methods for this run; a machine-wide
outage or firewall rules were excluded because other sessions and scheduled jobs
run on this workstation. So the 8 September regime remains untested.

**2. `HistoryRecovery` never ran.** It is the safety net built for exactly the
case above, and on every attempt it failed:

```
history recovery incomplete; checkpoint retained: Lark error 230027: Lack of
necessary permissions, ext=need scope: im:message.group_msg.
```

It failed *well*: it named the cause, wrote `recovery-error.txt`, **retained the
checkpoint** rather than advancing past messages it could not read
(`recovery.py:141`), retried every 60 seconds, and surfaced through
`co lark check` with exit 1. That is the correct behaviour for a blocked
recovery, and it is a clear improvement on 8 September, where the message simply
vanished with no explanation.

But it means the mechanism this gate exists to validate has still never
succeeded against a real connection.

## The scope is missing by construction, for everyone

`GET /open-apis/im/v1/messages` needs `im:message.group_msg`. The application
`co auth lark` creates does not have it — verified directly with the app's own
tenant token against the real chat id.

It is not only the automatic path. `docs/cli/feishu.md`'s manual instructions
list `im:message.group_at_msg:readonly`, `im:message:send_as_bot` and
`im:message.p2p_msg:readonly` — and not `im:message.group_msg`. The
"Recovering a disconnected listener" section says recovery "requires the bot's
message-history read permissions" without naming the scope.

So **no one following our own documentation, by either route, ends up with a bot
that can run history recovery.** That is why this could not be closed today, and
it is the single thing to fix before a repeat run.

## To repeat this run

1. Grant `im:message.group_msg` to the application and publish the version.
2. Re-run both variants above, and confirm `history recovery complete: N new
   message(s)` appears instead of the permission error.
3. Reproduce the 8 September fault properly — abort the transport and reject
   reconnects for longer than the heartbeat — so recovery is the only path left
   and is actually exercised.

Until then, the warnings in `docs/cli/feishu.md` and
`useful_skills/co-inbox/SKILL.md` telling users to treat a gap as possible
message loss stay as they are. Today's evidence does not justify removing them.

## Gate 3, re-run — passed

The scope was granted the way `lark-cli` does it, with no Developer Console
visit. From `cmd/event/console_url.go` (MIT, larksuite/cli):

```
{open-host}/page/launcher?clientID=<appID>&addons=<base64url(gzip(json))>
```

and its own comment on what that link is for: *"The bot-specific scan-to-enable
link adds the scopes to the app manifest, after which the tenant token carries
them."*

The page listed **"Act as app / Read all messages in associated group chat
(sensitive scope)"**; after Confirm, the same tenant token that had been refused
minutes earlier read the group's history with `code: 0`.

Three details decide whether that link works, and a first attempt got all three
wrong — producing a page that said "App updated" and granted nothing:

| | wrong | right |
|---|---|---|
| path | `/page/cli` (that is registration) | `/page/launcher` |
| identifier | `user_code` | `clientID`, camelCase, the app's own id |
| payload | `{"tenant": [...]}` | both `tenant` and `user` present as arrays |

### The run

| | |
|---|---|
| listener killed | `05:12:24` |
| during-gap message sent | `05:12:29` — `om_…6acae` |
| gap held | 90 s |
| listener restarted, connected | `05:14:04` |
| **`history recovery complete: 1 new message(s)`** | `05:14:05` |
| copies in `new/` | 1 |
| duplicates in `received.jsonl` | none, across all 4 messages of the day |

**Recovery is what delivered it.** The log carries no `received om_…` line for
this message, and that line is what the WebSocket path writes. Every earlier gap
in this document was covered by platform redelivery; this one was not, and the
safety net caught it. That is the first time `HistoryRecovery` has succeeded
against a live connection.

Immediately before the gap, a plain restart also logged `history recovery
complete: 0 new message(s)` — the path running clean with nothing to do, which is
what it should say when redelivery already did the work.

### What is now true

Gate 3's condition — nothing lost, nothing duplicated across a connection gap —
holds, and it holds by the mechanism designed for it rather than by luck of
platform buffering. The 8 September failure is explained: not a defect in
`reconcile()`, but a bot that was never allowed to read the history it was
written to read.

### Still not proven

The 8 September fault itself — transport aborted, reconnects rejected — was never
reproduced here; fault injection stayed at a process kill and a freeze by the
owner's decision. What this run shows is that when redelivery does *not* cover a
gap, recovery does.

## What was left in place

The listener was stopped. The group (`co185 acceptance 0915`, described in-band
as temporary) and the isolated inbox were **kept on purpose**: the repeat run
above needs exactly this setup, and rebuilding it costs another application, a
group and a user-scope authorization. Delete both once the repeat run has
passed.
