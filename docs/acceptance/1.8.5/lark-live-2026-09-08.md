## Failed release gate: message during the connection gap

The test used a temporary harness outside the source checkout. It aborted only
the test listener's established WebSocket transport and rejected that SDK
instance's reconnect attempts for 135 seconds. The server-configured heartbeat
was 120 seconds. SDK retry timing, event parsing, mailbox writes and provider
responses were unchanged. The workstation network and existing automations were
not interrupted. This is a controlled client connection failure, not a test of
every possible physical network fault.

- Socket connected: 13:10:41.011 UTC.
- Gap started: 13:10:59.385 UTC; synthetic @-mention sent at 13:11:04 UTC.
- Fault released: 13:13:14.388 UTC.
- SDK reconnected without restarting the process: 13:13:18.107 UTC.
- The gap message existed on Lark (confirmed by message-ID readback), but was
  absent from the candidate inbox. A fresh message after reconnect arrived.

At the final check, **175.1 seconds after reconnect**,
the gap message still had **0 inbox records**. The test listener was then
stopped; the two messages received before/after the gap had each been completed. Do not infer permanent provider
loss from a bounded observation, or mark this as passing merely because the SDK
reconnected. The current adapter has no history reconciliation path. It needs a
reviewed recovery design and a repeat of this real-channel test before the
release plan's no-loss-during-gap gate can pass.

Private raw evidence remains local; it must not be copied into a public PR.

## Proposed repair — repeat live run pending

startup/reconnect. It persists the first-start boundary and a checkpoint, advances
only after complete pagination, retries failures, expands known threads, retains

remain deduplicated across both delivery paths. `check` reports recovery failures.
The shutdown path waits for the history writer before releasing the listener lock.
