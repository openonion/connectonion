# When the door asked for your name and checked another guestbook

Opening remote `co rem` from a new browser tab is supposed to be a thirty-second ritual. The screen explained politely that the notebook belonged to the Host's owner, printed the exact `co trust admin add` command for the browser's key, and waited. We copied the command into the terminal, saw the green confirmation that `admins.txt` under `~/.co` had been updated, and clicked Retry. Instead of opening the notebook, the page slammed shut with `Agent error: forbidden: Denied by fast rules` and suggested checking whether `co ai` was still running.

The Host was very much running — in fact, it was the one saying no. Our first instinct was to suspect that `strict` trust did not admit administrators on its fast path without a separate whitelist entry. Yet opening `strict.md` disproved that in three seconds: `admin` sat right on the first line of `allow:`. So why did an address freshly written into `~/.co/admins.txt` arrive at the Host as a complete stranger?

Following `serve_project()` in `mac_bootstrap.py` revealed how quietly one identity had been split across two rooms. The always-on background service that `co init` installs lives inside a tidy internal profile folder under `~/.co/runtime/host` (or `mac-host` on macOS) so its `host.yaml` and logs stay out of the way. Because that internal folder has no keypair of its own, the Host inherits `~/.co/keys/agent.key` as its public face, and `serve_project()` explicitly points `rem_root` at `~/.co/rem`. Yet it passed `trust='strict'` as a bare string alongside `co_dir=runtime/.co`. Inside `server.py`, that bare string constructed a `TrustAgent` rooted in the internal runtime folder rather than `~/.co`. Every CLI command the owner ran — whether from their home directory or with `--global` — faithfully updated `~/.co/admins.txt`, while the background Host stood guard over an empty `~/.co/runtime/host/.co/admins.txt` that no command ever touched.

Looking closer at that seam turned up two smaller traps waiting right behind it. Passing a pre-built `TrustAgent` bound to `~/.co` fixed the directory split, except `server.py` immediately labeled any non-string trust parameter `"custom"` in the agent's metadata, skipped the startup banner's invite check, and still wrote WebSocket audit lines into the runtime folder instead of beside `~/.co/approvals.jsonl`. Meanwhile, down in `trust/tools.py`, `contacts.txt` and `whitelist.txt` folded hex addresses to lowercase on read while `load_admins()` compared raw case-sensitive strings — meaning a valid mixed-case key accepted by `co trust admin add` could still fail a lowercase lookup.

Binding the built-in global Host's `TrustAgent` and audit ledger directly to `~/.co` — while honoring whatever `trust:` level the operator configured in `host.yaml`, preserving that level's real name on `/info` and the banner, and folding case across admin checks — put the key, the notebook, and the guestbook back in the same room. When a service speaks with your global identity, every list that decides whom it trusts has to live beside that identity, not inside the closet where its launch file happens to sleep.
