# The database we built, and the attachment link that went nowhere

We thought we had already moved REM onto SQLite. Yesterday's release shipped a forty-six-megabyte `rem.db` with clean tables for people, organisations, tags, and messages, and our benchmark script cheered. Then we opened a real six-month notebook in the browser, clicked a cited contract PDF on a contact page, and nothing happened. Not an error banner, not a spinner — just silence. Meanwhile, in the background, a detached Python process burned sixty-two seconds of CPU rebuilding thirty-six megabytes of uncompressed JSON and HTML every time we marked a single thread done.

Both mysteries turned out to share the same root: we had built a proper database for the command line, while leaving the browser trapped in an older world designed around a thirty-one-megabyte offline `file://` HTML file.

Because the reader still expected to survive without a local server, `_snapshot()` walked right past `rem.db` and re-read thousands of Markdown pages, translations, run logs, and archived emails from disk on every change. Worse, the three-million-character excerpt budget filled up after the first thousand emails, starving forty-four percent of Outlook messages and every cited spreadsheet, web capture, and code file that came alphabetically later. And when an attachment *did* make it into the drawer, `attachments.py` handed the browser a `file:///...` link. From a `file://` snapshot that used to work by accident; from the live reader on `http://127.0.0.1`, every modern browser quietly refuses to cross into the local filesystem. Even the preview text underneath had been flattened with `" ".join(text.split())` and chopped off at six hundred and forty characters, turning multi-sheet spreadsheets and contracts into a single breathless paragraph.

Looking under the hood of `rem.db` itself revealed one more quiet tax. Editing a single person or organisation page triggered a fallback that ran `DELETE FROM` across six tables without `auto_vacuum`, leaving more than forty percent of the database file as dead freelist pages, while an idle tab polled `/rem/translate-all` once every second and re-scanned a thousand Markdown files on disk just to check whether a translation job was running.

Once we decided to stop straddling two worlds — serving the local reader directly from the CLI's loopback Host instead of rebuilding offline `file://` dumps on every click — every piece simplified at once. `rem.db` moved to schema v3 with persistent WAL, incremental vacuum, per-record upserts, external-content FTS5 with CJK search, and cached attachment text, translations, and research captures. The Host gained a strict loopback `/rem/attachment` stream and gzip compression, letting PDFs open in an inline frame, images render natively, and spreadsheets keep their rows intact without ever exposing active HTML on the Host origin. Sometimes finishing a migration is not about adding another layer; it is about letting go of the fallback that kept the new layer from doing its job.
