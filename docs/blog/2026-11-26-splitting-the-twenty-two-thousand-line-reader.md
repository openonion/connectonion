# Splitting a twenty-two-thousand-line HTML file without adding a build step

When we first built the disposable `co rem` notebook reader, putting the whole page inside a single `reader.html` file felt like an obvious win. An offline snapshot had to open directly from `file://` with double-click simplicity, zero external network requests, and no local web server, so keeping markup, styles, and scripts together in one file matched the job. Thirty-one release candidates later, we ran `wc -l` after a bruising real-notebook audit and stared at the number: 22,113 lines and 1.67 megabytes in a single file. Only thirty-one of those lines were actual `<body>` markup. Around them sat seven separate `<style>` blocks stacked chronologically like geological strata totaling nearly five thousand lines, followed by one seventeen-thousand-line `<script>`. Worse, the bugs we had just spent all day fixing were direct symptoms of that monolith: a short `.pl` selector written for project rows silently drew black borders across command-palette items two thousand lines away, a later `<style>` block's `:has()` selector crushed the evidence drawer,parallel agent worktrees collided on the same file, and fifty unit test suites had resorted to slicing individual JavaScript functions out of the HTML string with regular expressions just to run them in Node.

Our first instinct was to ask whether we had outgrown vanilla JavaScript altogether and ought to rewrite the reader in React with Vite compiling everything back into a single HTML bundle. On paper that sounded modern and clean, until we traced what a compiled bundle actually does inside a pure-Python CLI repository where several coding agents work in parallel git worktrees every day. Because `pip install connectonion` ships through `hatchling` onto machines that may not have Node installed, we would either have to commit a megabyte of compiled bundle output to git—guaranteeing unresolvable merge conflicts across every concurrent worktree that touched a single component—or force Node and Vite into all twenty-two Python CI shards and every contributor's `pytest` loop. Even worse, rewriting twenty-two thousand lines of battle-tested privacy curtains, custom week-grid geometry, and WebGL graph interactions would invite weeks of classic second-system regressions while giving up our favorite property of the reader: opening Chrome DevTools on any live or offline page shows the exact, unminified line of source code sitting in the repository.

Once we separated how humans and agents author source files from how `reader.py` delivers a page, the false choice between a twenty-two-thousand-line file and a Node bundler vanished. The delivery artifact still needs to be one self-contained HTML string, whereas the source tree needs crisp, single-purpose domain boundaries where anyone can see at a glance where a feature lives. We carved `reader.html` along its natural domain seams into `connectonion/rem/reader_ui/`, pairing a seventy-one-line `shell.html` skeleton with six domain stylesheets (`tokens.css`, `shell_and_reading.css`, `today_and_overview.css`, `organisations.css`, `knowledge_graph.css`, and `desk_and_open.css`) and thirteen focused script modules (`i18n_and_boot.js`, `privacy_and_theme.js`, `markdown_and_tags.js`, `page_facts_and_threads.js`, `rail_and_settings.js`, `today_cards.js`, `waiting_and_desk.js`, `people_and_keys.js`, `agenda_and_projects.js`, `orgs_skills_sessions.js`, `record_and_search.js`, `knowledge_graph.js`, and `router_evidence_palette.js`). Every file stays well under a hard 2,200-line ceiling, catch-all names like `utils` or `helpers` are banned by test, and each script and stylesheet is checked in isolation so an unclosed brace or comment in one module can never bleed into the next.

To keep all fifty existing test suites and snapshot caches working without rewriting callers, we backed `reader.TEMPLATE` with a lightweight `ReaderTemplatePath` subclass of `pathlib.Path` in `reader_template.py`. Calling `TEMPLATE.read_text()` concatenates the manifest in memory in under two milliseconds, keyed by the nanosecond modification times and byte sizes of all twenty source files, while `TEMPLATE.stat()` exposes the newest `st_mtime_ns` across `reader_ui/` so editing any single CSS or JS module immediately invalidates saved reader snapshots. When we verified the assembled output against the original monolith, the seventeen-thousand-line JavaScript payload matched down to the exact SHA-256 digest (`44acf89788...`), every non-blank CSS rule stood in identical cascade order inside one clean `<style>` block, pure modules like `markdown_and_tags.js` ran directly in Node without regex surgery, and all 786 unit, wheel-install, and real-notebook tests passed without a single Node dependency in sight.
