# A familiar name is not an identity

REM's relationship search could pick the first page whose title matched a name.
Ordinary search could then show that person's facts as Best match. Both behaviors
used record order to answer a question the notebook had not resolved.

A read-only census found three same-title groups across six eligible People pages.
That is enough to require a choice. It is not evidence that the records describe
the same people, and it does not justify combining their contacts or histories.

The navigation candidate now offers each eligible exact page with available
original Company, Role, Email or other facts under the privacy filter. Ambiguous
name searches do not promote one person's facts. Relationship searches wait for
an exact page choice; unique names keep the direct route. A stale or ineligible
choice never falls back to another person with the same title. Missing visible
identifying facts are stated honestly.

Seven contracts failed before the change; one unique-name control passed. The
focused reader suites now pass, including original facts under cached translation
and private-field removal. Those are logical contracts, not native interaction
acceptance. Current desktop, phone, keyboard and accessibility checks are pending.
No private notebook data was rewritten, and no collection or model run was started.

Tracked in existing issue #2197 and draft PR #2633. This remains an unreleased
navigation candidate; the currently installed public preview is 1.9.3rc16.
