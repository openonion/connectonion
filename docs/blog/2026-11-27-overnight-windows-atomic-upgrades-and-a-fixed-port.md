# Twenty-four minutes without a CLI

At 19:33 on a Sunday evening, someone ran a routine preview upgrade on their Mac with `uv tool install --force` and walked away. Halfway through downloading wheels, the command aborted, and because `--force` deletes the existing tool environment before the replacement is ready, `~/.local/bin/co` simply ceased to exist for the next twenty-four minutes. Nobody noticed until the scheduled REM clock fired in the dark and slammed straight into `ModuleNotFoundError: No module named 'connectonion'`, leaving a traceback in `launchd.log` and an orphaned night turn.

At first glance that looked like a packaging bug you could patch with a retry flag, until we traced what actually happens on a laptop between midnight and breakfast. An unattended upgrade does not happen in a vacuum: a scheduled REM turn might already be holding `exec-turn.lock`, a background `co ai` Host might be serving an open reader tab from yesterday's release, and every continuation turn firing past six in the morning quietly bites into the user's daytime five-hour rolling agent quota. Treating the installer, the overnight clock, and the morning reader as separate scripts meant each one could trip over the other while the owner was asleep.

The turning point came when we stopped upgrading in place altogether. Instead of letting `uv tool install --force` wipe the live environment first, `co rem upgrade` now stages the candidate release inside an isolated temporary `UV_TOOL_DIR`, imports `connectonion`, and runs `co --version` against the staged binary before touching anything live. If a REM turn holds `exec-turn.lock`, it defers until the notebook is idle; if the download or verification fails, the temporary directory vanishes and the previous `co` keeps running untouched while `co rem status` and `co rem doctor` surface the failure. Only after the staged environment passes every check do we back up the live tool directory, promote from warm cache, verify again, and roll straight back if the swap misbehaves—with a thin shell guard around scheduled triggers so even a manual mid-upgrade race logs one clean skip line instead of a traceback.

Once the swap itself became atomic, the rest of the midnight-to-morning handoff snapped into focus. Right after a verified upgrade lands, the newly installed Python kicks off a background prewarm of `live.html` and `data.json` and replaces the idle live Host on REM's dedicated preferred port (`18765`), while the opt-in five-start `overnight` profile concentrates upkeep between midnight and `03:00` with a hard `03:30` continuation cutoff so morning coding starts with a full five-hour quota window and a warm, single-tab reader already on the new release. The real lesson was not about `uv` flags at all: anything that runs while the user is asleep must treat "nothing broke and nothing moved under your feet" as its primary invariant.
