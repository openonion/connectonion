# 610 of 1,402

An agent was filling in a post for Kim: 1,402 characters, typed into the
composer with `co browser keyboard_type`. The CLI gave up at 120 seconds. By
then 610 characters were in the box, and the agent went on with what it had.

Nothing was broken. `keyboard_type` was doing what it was written to do:
type Latin text one key at a time, with a person's rhythm. That is a small
pause between keys, a longer one at each space, and now and then a hesitation.
It comes to about a tenth of a second a character. A title takes 15 seconds.
A long post takes longer than the command is allowed to run.

## One event instead of 1,402

The fast path was already in the code. Chinese text has always gone in by
paste, because that is how people enter it: put it on the clipboard, press
Cmd/Ctrl+V, check that the field's text changed, and put the clipboard back.
A lock shared by every tab keeps two tabs from pasting each other's words.

Now every text goes that way first, Latin included. A paste is one event,
however long the text is. It also leaves no stretch of time in which focus can
wander to another field halfway through.

When a field refuses the paste, the text is typed as before: key by key for
Latin, IME composition for Chinese, Japanese and Korean.

## Typing like a person is now something you ask for

Some fields care how they are typed into, such as a login form or a search box
that suggests as you go. For those there is a flag:

```bash
co browser keyboard_type "kim@example.com" --human
```

The test that matters types a 1,404-character text into a stand-in editor. It
asserts one paste, no per-key events, and the clipboard restored. On the old
code that test fails; with the change it passes. See #2901.
