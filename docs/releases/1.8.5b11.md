# ConnectOnion 1.8.5b11 — beta

Beta, 15 September 2026. The command line says what to run next, and calendar
invitations actually reach people.

Stable stays **1.8.4**. This is not Latest and needs an explicit pin or
`--pre`:

```bash
python -m pip install --pre connectonion==1.8.5b11
co --version
```

## An invitation now reaches the attendee

Google's events API defaults `sendUpdates` to `none`, and we never passed it. So
this:

```bash
co gcalendar meet "Intro" ... --attendees guest@example.com --yes
```

created the event, printed a Meet link, and **told the attendee nothing**. It
cost a live client meeting on 15 September, whose guest put it plainly: *"Didn't
get an email invite but anyway there is a Google Meet link there."*

The same gap sat on update and delete, which is worse than never inviting
anyone — somebody who *was* invited is never told the meeting moved or was
cancelled, so they hold the old slot and arrive at a dead link.

What let it survive is the other half: `Event created` read **identically**
whether three people were invited or nobody was. The silent failure was
indistinguishable from success. So the confirmation now names them, and the
line's absence is equally the signal:

```
Event created: Kickoff
Start: 2026-09-15 04:30 PM +10:00
Invitations sent: a@example.com, b@example.com
```

That time is also new. A meeting entered as `16:30+10:00` used to confirm as
`06:30 AM` — the right instant, described in a way no reader interprets
correctly. It is now confirmed in the zone it was written in, so the line can be
compared with what was typed rather than converted in your head. A time given
without a zone is UTC, and says so.

## The command line points somewhere you can run

Audited against `useful_skills/cli-skill-design` by running its checks rather
than asserting its principles. Four things failed.

**Every deliberate refusal printed two next steps.** `co env set
LARK_APP_SECRET x` put `Next: co auth lark` on stdout and `Next: co --help` on
stderr, so anyone merging streams — most callers — read the useless one first.
The skill names this exactly: *"One next step. Two tips is a fork, and the agent
resolves a fork by guessing."* It affected 25 deliberate exit-2 sites across 8
modules, so it was the whole refusal surface.

**A typo ended at a flag.** Every mistyped command said `co --help`, even when
Click had just worked out the answer:

```
co larc          → Next: co lark
co lark recieve  → Next: co lark receive
co like          → Next: co commands
```

When there is a guess it is now the next command, in context. When there is
none, the fallback is `co commands` — all 199 commands, one per line with a
summary — rather than a boxed screen of groups.

**Two failures named no command at all.** `co auth feishu --app-id bogus`
described the shape of an application id and stopped. `co <provider> check`
said "Check bot history permissions and network", an instruction covering two
unrelated causes.

**The `co env` skill never learned about 1.8.5b9.** `co env rotate`, `--secret`
and `--from-console` all shipped and none were in it, so an agent driving
`co env` did not know encrypted storage existed.

Tip test, output only, model pinned: 9 of 9 commands produced a real command
that advanced the stated goal.

## A missing permission is one link away

`co <provider> check` turns the platform's own `need scope: X` into a link that
grants it:

```
History recovery is incomplete: Lark error 230027: … need scope: im:message.group_msg
The bot is missing a permission. This is a sensitive scope: it lets the app read
every message in the groups it is in.
Open this, approve it, and the listener picks it up on its next retry:
https://open.larksuite.com/page/launcher?clientID=cli_…&addons=…
```

One command, one click, no Developer Console. `co auth` also declares the scopes
and events the inbox needs at registration, so a new application arrives able to
do the work rather than able to receive and then fail at the first gap.

## The reconnect gate passed

#1462's gate 3 — nothing lost or duplicated across a connection gap — has been
the one thing between this line and stable since 8 September. It passed on 15
September, and the reason it had not is the permission above: history recovery
had never once been allowed to run.

Measured: listener killed, a message posted during a 90-second gap, listener
restarted → `history recovery complete: 1 new message(s)`, queued exactly once,
with no WebSocket delivery line for it. Recovery is what delivered it.

The documentation that told you to treat a gap as possible message loss is gone,
because it is no longer true. See
[the run](../acceptance/1.8.5/lark-live-2026-09-15.md).

## Known limits

Stable is still 1.8.4; cutting `X.Y.0` is a deliberate decision, not a
consequence of a green checklist.

That run reproduced a killed listener and a frozen one, not a transport aborted
with its reconnects rejected. What it shows is that when the platform does not
redeliver, recovery does.

A chat message can command the agent with no sender allowlist until 1.9. A
browser that exits on its own takes the tab registry with it (#1513). `co
browser` can list and switch to a page the site opened, but cannot yet adopt one
under a name or auto-track a popup (#1525, targeted 1.8.6).
