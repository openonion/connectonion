# ConnectOnion 1.8.5

Stable, 15 September 2026. A chat bot is a directory of files, and the command
line tells you what to run next.

```bash
python -m pip install --upgrade connectonion==1.8.5
co --version
```

This replaces **1.8.4** as the default `pip install connectonion`.

## A Feishu or Lark bot, as a directory

The headline of this release. One process holds the connection and writes every
message into `~/.co/inbox/<provider>/`; anything that can read a file can answer
it. Nothing in that directory knows what an agent is.

```bash
pip install lark-oapi
co auth lark                        # scan once; the application exists, keys saved
# add the bot to a group and @ it
co lark ls                          # what is waiting
m=$(co lark receive)                # take one; the take is a rename(2), so two
co lark reply "$(echo "$m" | jq -r .id)" "on it"
```

Or hand every message to a program and let it loop:

```bash
co lark consume -- claude -p        # its stdout becomes the reply
```

Nine verbs — `listen receive send reply done check ls log consume` — identical
under `co feishu` and `co lark`. The full reference is
[docs/cli/feishu.md](../cli/feishu.md).

**What the queue promises.** Taking a message is an atomic rename, so two
consumers never get the same one. A claim expires after an hour and the message
comes back, which is why `done` is not optional. A reply happens once unless you
pass `--again`. Nothing is ever deleted — `received.jsonl` is your history.

**And across a disconnection.** A message sent while the listener was down is
read back from the conversation's history on reconnect, deduplicated by the
provider's own message id, and queued exactly once. This was the last gate on
this release and it is the one that took longest to close; see *Acceptance*
below for what was measured and what was not.

## The command line names what to run next

Every command, success or failure, ends by naming the next one — spelled out,
with the argument shape filled in. That contract is now audited rather than
asserted, against `useful_skills/cli-skill-design`, and the audit found four
ways it was being broken.

```
co larc            → Next: co lark              # the guess, runnable
co lark recieve    → Next: co lark receive      # in its group
co like            → Next: co commands          # nothing matched: all 199, one per line
```

A refusal names **one** next step. It used to name two — the command's own
precise tip on stdout and a generic `co --help` on stderr — and anyone merging
streams, which is most callers, read the useless one first. That affected every
deliberate refusal across the CLI.

`co commands` lists all 199 commands, one per line with a summary. `co doctor`
diagnoses the install. Both are the answer to "what can this thing do" without
reading a boxed help screen.

## Settings, and secrets

`co env` shows which file an invocation selected and what it holds, with values
hidden unless you ask:

```bash
co env                              # file, settings, sources, next step
co env set OPENAI_API_KEY "$KEY"
co env get MODEL                    # bare value, for $(...)
```

A value that should not sit in a file in plain text can be encrypted, under a
key derived from this agent's own key and stored nowhere:

```bash
co env set LARK_APP_SECRET <value> --from-console --secret
co env rotate LARK_APP_SECRET       # re-encrypt under the next derived key
```

There is no master key to back up and no keychain to be unreachable on a machine
with no logged-in human — which matters because a `co deploy --to` server has
neither. Your recovery phrase still reaches the value on another machine; the
file holding those twelve words does not need to exist for the store to work.

## A missing permission is one link away

When a bot lacks a scope, the CLI turns the platform's own error into a link
that grants it:

```
History recovery is incomplete: Lark error 230027 … need scope: im:message.group_msg
The bot is missing a permission. This is a sensitive scope: it lets the app read
every message in the groups it is in.
Open this, approve it, and the listener picks it up on its next retry:
https://open.larksuite.com/page/launcher?clientID=…&addons=…
```

One command, one click. `co auth` also asks for the scopes and events the inbox
needs when it creates the application, so a new bot arrives able to do the work.

## Calendar invitations reach people

`co gcalendar` never passed Google's `sendUpdates`, which defaults to `none`. An
event created with `--attendees` invited **nobody**, and moving or cancelling one
told its attendees nothing — worse, because they hold the old slot and arrive at
a dead link.

What let it survive is that `Event created` read identically whether three people
were invited or none. It now names them, and echoes the time in the zone it was
written in rather than converted:

```
Meeting created: Intro
Start: 2026-09-15 04:30 PM +10:00
Invitations sent: guest@example.com
```

## Also in this line since 1.8.4

- **The paid browser installs from PyPI** and runs on Intel Macs. `pip install
  'connectonion[wtf]'`; the browser binary stays licence-gated.
- **A page the site opened for itself can be reached** — a payment popup, any
  `target="_blank"` link. `co browser list_pages` shows the browser's real pages
  and `switch_page <index>` points a session at one.
- **`co browser wait` takes seconds**, is capped at 60, and refuses a wrong value
  before taking the tab lock rather than holding it for forty-one minutes.
- **`co auth lark` works on data-residency tenants.** It had been printing the
  platform's `/page/launcher` URL, which cannot complete the flow; it now builds
  `/page/cli`, as `lark-cli` does.

## Acceptance

The reconnect gate was measured on a live Lark tenant, not simulated: the
listener was killed, a message posted during a 90-second gap, and the listener
restarted. History recovery delivered it — `history recovery complete: 1 new
message(s)`, queued exactly once, with no WebSocket delivery line for it. Four
messages across the day's runs, no duplicates. The full record is
[docs/acceptance/1.8.5/lark-live-2026-09-15.md](../acceptance/1.8.5/lark-live-2026-09-15.md).

**Not claimed.** That run reproduced a killed listener and a frozen one, not a
transport aborted with its reconnects rejected. What it establishes is that when
the platform does not redeliver, recovery does.

## Known limits

- **No sender allowlist.** A chat message can command the agent, and the only
  filter is the platform's own — a group message must @ the bot. Who may command
  an agent belongs to whatever consumes the directory, and a first-class
  allowlist is #1479, targeted 1.9.
- **The inbox does not record which consumer handled a message** (#1503). With
  several consumers on one directory, `done.jsonl` says a message was handled,
  not by whom.
- **A browser that exits on its own takes the tab registry with it** (#1513).
- **`co browser` cannot adopt a page it did not create under a name**, so a
  multi-step flow through a popup needs `switch_page` on each command (#1525).
- `co env pull` and `co browser import` were planned for this release and are
  not in it; both moved to 1.8.6 (#1476, #1477).
