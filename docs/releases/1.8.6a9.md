# ConnectOnion 1.8.6a9

**Preview.** `pip install --pre connectonion` — a plain `pip install` stays on
stable 1.8.5.

Nothing is not a message.

## A successful send of nothing

```
$ co whatsapp send 120363411567190840@g.us      # the text was missing
3EB051DF0FC1EF995EF15B
$ echo $?
0
```

The command read stdin, reached EOF, and delivered an empty bubble into the
group. An id was printed. The exit code was 0. `sent.jsonl` got a row saying it
worked:

```json
{"at":"2026-09-19T01:09:23Z","chat":"120363411567190840@g.us","text":"","id":"3EB051DF0FC1EF995EF15B","ok":true}
```

Every habit that catches a bad send reported success — including reading the
record back afterwards, which is the one that catches almost everything else.
It could not help here, because the record was accurate. It really was a
successful send. Of nothing.

This happened twice on 19 September, from a stray fragment left in a shell
line. One of the blanks landed in a customer's group.

## Now it is a usage error

```
$ co whatsapp send 120363411567190840@g.us
nothing to send: the text was empty. Pass it as an argument or on stdin
$ echo $?
2
```

Empty or whitespace-only text is refused on `send`, `reply` and `edit`. Nothing
is sent and **nothing is written to `sent.jsonl`** — a refusal is not an
attempt, and a row there would make the log claim a send that never happened.

Two details that matter more than the check itself:

- **A refused `reply` does not consume the question.** `reply` marks a message
  answered; losing the question to a typo would be worse than the blank. The
  refusal happens before anything is marked, and before the "answering"
  reaction goes out — so nothing tells the sender an answer is coming.
- **`--plain`-style edge cases still go.** The check is on what the caller
  wrote, not on what survives rendering: `**!**` is a real message.

## Why a required argument was worth a release

It was a caller's mistake, and it would be easy to leave it there. But the
failure is shaped so the caller cannot see it: the command looks like it
worked, the blank lands in somebody else's room, and until 1.8.6a8 there was no
way to take it back.

That last part is the reason this is a9 and not a note in a backlog. The
undo shipped an hour earlier — and the first thing it was used for was
deleting these blanks out of a customer's group.

Closes #1602. The undo it depended on is #1601, in 1.8.6a8.
