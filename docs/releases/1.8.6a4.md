# ConnectOnion 1.8.6a4

**Preview.** `pip install --pre connectonion` — a plain `pip install` stays on
stable 1.8.5.

The bot knows who is talking, what they mean, and when it has stopped listening.

## Everything here came from running it in production

Three reports, all from using the thing rather than reading it.

**A sender has a name.** Messages arrived from `126121882435737@lid`, which
tells nobody who spoke, and every consumer was going to build the same lookup —
we already maintain one for Lark for exactly this reason. `sender_name` is now
on every message, read from the contacts whatsmeow already synced: 2020 rows
after history sync, 857 of them keyed by `@lid`, with `whatsmeow_lid_map`
bridging the two forms. No API call, so a name costs a point lookup rather than
a round trip on the path every message takes.

Read fresh per message rather than cached, because names change and a stale name
is worse than an opaque id — it reads as authoritative. A broken or missing
session file yields an empty name, never an exception: a missing name must not
cost the message.

**A consumer can ask for the conversation.** A group asks things across several
messages — *"the price sheet is wrong"*, *"it's missing the cleaning column"*,
*"@bot recompute"* — and the consumer was handed the third alone.

```bash
co whatsapp receive --context 20
co whatsapp consume --context 20 -- claude -p
```

`mention_only` had been doing two jobs under one name: deciding *when the bot
speaks* is right, and deciding *what the bot is allowed to know* came along
silently. Those are different questions. Our own replies are in the transcript
too — one without them reads as though the bot never responded, and a model
given that apologises for ignoring someone it already helped.

Opt-in and zero by default. Without the flag the line is byte-identical. Those
turns are other people's messages, which is the right shape for a flag someone
typed rather than a default they inherited.

**A listener that can never receive again stops.** A session in production
stopped working: `send` failed, `check` was green, and `listen` reported
normally and received nothing, forever.

We were handling three of neonize's thirty-seven events. `LoggedOutEv`,
`StreamReplacedEv` and `TemporaryBanEv` were all arriving and being discarded,
so a phone unlinking the device left a process holding a socket that would never
deliver again — and *"nobody has messaged us"* was indistinguishable from
*"we were logged out yesterday"*.

Those three now stop the listener with a reason and **exit 3**, the same code as
a missing credential, because it is the same kind of problem: a person has to
act before any restart helps. The rest — disconnections, keepalive timeouts —
became log lines, which is what a later *"could we have missed a message?"*
needs to see.

Two smaller ones alongside: `check` no longer claims the QR was never scanned
when the device was logged out (whatsmeow clears the same tables for both, so it
now says both), and `send` stops quoting whatsmeow's `the store doesn't contain
a device JID` at people.

## Verified

- `sender_name` against the **real** 2020-row contact store, resolving the
  production sender nobody could identify.
- The quoted reference and the message kind against protobuf's own generated
  classes rather than test doubles.
- The listener's terminal events by driving the real `run()` over a socket that
  fires them — four of those tests confirmed red first, by downgrading the fatal
  handler to a log line.

Offline suite: 10,316 passed.

## Known, and not fixed here

- `chat_name` — group subjects are not in the local store, so a group's name is
  an API call per group. A different cost profile that belongs with a decision
  about caching it.
- Edits, revokes, forwards, group lifecycle and view-once messages have no
  defined shape (#1590). Each row needs a product decision before it needs code,
  and none of them has been hit in production.
