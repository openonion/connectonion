# ConnectOnion 1.8.6a2

**Preview.** `pip install --pre connectonion` — a plain `pip install` stays on
stable 1.8.5.

The bot answers where it was asked, and says so while it works.

## What this release is

1.8.6a1 shipped WhatsApp as an inbox provider with one honest caveat in its
release notes: it had never been accepted against a real account. This is the
release where it was, and everything below except the last section is something
that acceptance found.

That is the shape worth naming. Five of these seven fixes were invisible to
every automated signal we had — the tests passed, the process was up, the
command exited 0 — and were found only by a person sending a message and asking
where it went.

## WhatsApp

**An @mention registers whichever id the group addresses you by.** WhatsApp is
migrating accounts to LID addressing: in a migrated group an @mention carries
the account's LID, which shares no digits with its phone number. The linked
device holds both and we read only one, so a real mention arrived as
`mentioned: false` and a `mention_only` channel sat silent while being
addressed. Identity is now the set of ids the account answers to. The connect
line names both, which is what makes the next one of these a glance rather than
an investigation.

**Every message is readable on protobuf 7.** protobuf 7 removed
`FieldDescriptor.label`, which was read on the first field of every message, so
on a fresh install every message was logged as "event not understood" and none
reached the inbox.

**`check` calls a device linked only once a phone has confirmed it.** It used to
ask whether `session.db` existed — a file created before the QR is even drawn.
A pairing that timed out left the file behind and `check` answered
`✓ whatsapp reachable` with no device.

**A reply quotes the message it answers.** The reply reached the right chat, and
arrived as a loose line while `sent.jsonl` recorded that it had answered a
specific message. WhatsApp carries the quote inside the outgoing message, so it
is rebuilt from the inbox log rather than by retaining everyone's raw traffic.

**The queue is visible from inside the chat.** A message the bot will answer is
marked as it enters the queue and re-marked when an answer is actually on its
way. The minutes between — a model thinking, a consumer running — used to be
indistinguishable from a bot that had crashed. It doubles as the cheapest
debugger available: no mark means it never arrived, the first mark alone means
nothing picked it up, the second with no answer means the reply path failed.
`CO_INBOX_REACT=0` turns it off.

**The extra names the system library pip cannot supply.** `pip install
'connectonion[whatsapp]'` succeeded and the next command answered "The WhatsApp
library is not installed. Run: pip install 'connectonion[whatsapp]'". neonize
needs libmagic, which comes from brew/apt/dnf.

## Mail

**A date window keeps its recent end.** `co outlook inbox --since 30d` returned
the *oldest* ten messages in the window and silently dropped the rest — asked
what arrived in the last month, it answered with mail from a month ago. It now
walks from the recent edge and says on stderr when the cap cut something, so
`--json` stays exactly one array on stdout.

**A listing number carries which listing it came from.** `co outlook inbox`
followed by `co outlook cancel 1` resolved row one of the *inbox* and deleted a
received email, printing a green tick and exiting 0. Both listings numbered from
1 into one cache and nothing recorded which was which. Numbers are now scoped to
their listing, and `cancel` refuses anything that did not come from `co outlook
scheduled`.

Graph's delete is a soft delete, so nothing was destroyed permanently — but the
command reported success for an action it did not perform and exited 0, which is
the part that matters.

**Errors go to stderr.** `co outlook inbox --json > mail.json` was collecting
failures into the file it was meant to fill.

## Local models

**An unreachable local model is diagnosed as a local model.** A failed request
to `127.0.0.1` used to advise checking your internet connection and disabling
your VPN. Local addresses now get causes that can be true of them, and ollama's
own port names `ollama serve`. Remote endpoints are unchanged.

## Verified

- WhatsApp, live, on the owner's own number in a real group:
  `docs/acceptance/1.8.6/whatsapp-live-2026-09-17.md`. Inbound in both
  directions (`mentioned` true and false), reply, reconnect without a QR,
  deduplication, and `check` on both a linked and an unlinked session.
- Ollama, against the **installed** 1.8.6a1 wheel with every cloud credential
  removed and an empty `HOME`: local text, structured output, a tool-capable
  model calling a real tool, and four separate checks that no cloud key is
  reachable and nothing falls back silently. 17 of 17.
- Outlook deferred send and reply (#1221, #1417, #910), on a real mailbox,
  self-addressed: held rather than delivered, **and delivered when the time
  came** — scheduled 05:45:07Z for 05:47:07Z, arrived 05:47:30Z — plus an
  attachment downloaded from the received copy and byte-compared with the
  original.

Offline suite: 10,259 passed.

## Known, and not fixed here

- A non-text WhatsApp message (image, sticker, voice) arrives with an empty body
  and no field saying what kind it was, so it cannot be told from someone
  sending nothing (#1566).
- `co gmail inbox --since --json` still refuses the combination, while the same
  pair works on Outlook (#1569).
- A consumer is handed one message and no conversation (#1565).
- The calendar full journey — invite, accept, add attendee, reschedule, cancel —
  has not been run against a real account (#1547).
