# ConnectOnion 1.8.5b9 — beta

Beta, 15 September 2026. An app secret can be encrypted, and the auth command
that made you type one now tells the truth.

Stable stays **1.8.4**. This is not Latest and needs an explicit pin or
`--pre`:

```bash
python -m pip install --pre connectonion==1.8.5b9
co --version
```

## `co env set --secret`

A value can be stored encrypted instead of in plain text, and rotated:

```bash
co env set LARK_APP_SECRET <value> --from-console --secret
co env get LARK_APP_SECRET
co env rotate LARK_APP_SECRET
```

The file holds ciphertext at `0600` in a `0700` directory. `co env get` still
answers, because it is the substitution form of the command — the encryption
changes what sits on disk between uses, not what a caller asking by name
receives. The encrypted store is consulted **last**, after the process
environment and the env file, so adding it cannot change what any existing
setup already resolves to.

### No master key, therefore no keychain

[1.8.5b8's notes](1.8.5b8.md) said putting secrets in the OS keychain was #1497,
targeted 2.x, and that unattended paths — launchd, SSH, `co deploy --to`
servers — have no reachable keychain at all. That second fact is what made the
first one solvable earlier than 2.x, by not needing a keychain.

`lark-cli`, the reference implementation, generates an AES-256 master key and
keeps it in the OS keychain because it has no other secret to start from. We
have `derive.py`, which already turns a secret into a tree of keys — so the
encryption key is *derived at a path* and thrown away. There is nothing to
store, therefore nothing to put in a keychain, therefore nothing to be blocked
by a sandbox, a denied prompt, or a machine with no logged-in human. And
`slip13_path` already carries a rotation index whose entire purpose is this, so
`co env rotate` is "derive at index + 1, re-encrypt" with no key-wrapping
scheme to design.

### Rooted at the agent key, not the phrase

The root of the subtree is `.co/keys/agent.key`, which `address.load()` already
opens on every command — deliberately **not** `.co/keys/recovery.txt`.

The phrase file is optional. `co keys` prints "missing" for it without
complaint, and writing the twelve words on paper and deleting the file is the
correct thing to do with a recovery phrase. A store rooted there would have
meant that doing the right thing with your backup silently made every stored
secret unopenable, with no error pointing anywhere near the cause — and that a
routine `co env get` opened the most sensitive file on the machine every time.

Nothing is given up by rooting one level lower, because `agent.key` is itself
`derive_path(seed, slip13_path(ACCOUNT_URI))`. The twelve words still reach
every secret, through the agent key rather than around it:

```
twelve words ──BIP-39──▶ seed ──SLIP-0013──▶ agent.key ──SLIP-0013──▶ secret key
```

So a new machine still decrypts from the words alone. It just no longer reads
them to do ordinary work.

## `co env set --from-console`

`co env set LARK_APP_SECRET` refused a hand-typed value and pointed at
`co auth lark` — correctly in general, since a typed app secret has no checkable
source. But on a data-residency tenant `co auth lark` cannot create an
application at all, so the two rules pointed at each other with no way out.

`--from-console` opens that door, and only that door: it is accepted on
`FEISHU_`/`LARK_` app credentials, and passing it on any other key is an error
rather than a no-op, so it cannot quietly become how people set everything.

## The scan link says what it is

`co auth lark` said its link lasted ten minutes. It does not — that number was
the SDK's fallback, and the server returns 3600. The TTL now comes from the
server every time, and when the field is absent the command says the platform
did not say, rather than inventing a figure.

More usefully, it now explains the thing that actually happens on some
data-residency tenants: `open.larksuite.com/page/launcher` strips `user_code`
on load and renders **"Link expired"** while the poller is answering
`authorization_pending` in the same second. The code was alive the whole time;
the page never read it. Four codes were spent before the word on the screen was
doubted.

```
This link is valid for 60 minutes (3600s).

If that page says "Link expired" straight away, the code is almost
certainly still alive and this flow cannot create an application for your
tenant — some data-residency tenants are served a launcher that drops the
code. Reusing an existing application with --app-id goes through the same
page and fails the same way.
  Create the application in the Lark Developer Console instead, then put
  its id and secret in the env file with:  co env set
```

The `--app-id` line is there because it was tested: same endpoint, same
launcher, same "Link expired". A remedy that cannot work sends the reader in a
circle with the confidence of an instruction.

## Known limits

Retrieval is plaintext by design. `co env get` prints the decrypted value
because that is what the command is for; `co env show` is the browsing command
and redacts by default. What encryption removes is a secret sitting at rest in a
file people `cat` in a screen share, paste into an issue, and read aloud on a
call.

Anyone who can read `.co/keys/agent.key` can decrypt the whole store. That
person can already sign as the agent, so the store is not what they would
attack; it is stated here rather than implied.

There is no region-local Lark accounts host to fix the launcher with —
`accounts.jp`, `accounts.sg` and the tenant host all return 404 — and it cannot
be pre-checked, because a server-side GET of the launcher returns 200 with the
code intact and the verdict is rendered client-side. The command now tells the
truth about a platform limitation it cannot remove (#1537).

Unchanged: the no-loss-across-a-reconnect gate in #1462 has not passed, which is
why stable is still 1.8.4. A chat message can command the agent and there is no
sender allowlist until 1.9. A browser that exits on its own takes the tab
registry with it (#1513, targeted 1.8.6).
