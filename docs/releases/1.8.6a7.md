# ConnectOnion 1.8.6a7

**Preview.** `pip install --pre connectonion` — a plain `pip install` stays on
stable 1.8.5.

The diagnostic stops claiming the network.

## `check` was asserting something it never looked at

```
$ co whatsapp check
✓ whatsapp reachable · listener pid 13813 · 0 unread
```

That word came from four facts: a package being importable, a row in
`whatsmeow_device`, a timestamp inside a shared library, and a pid in a lock
file. **None of them is the network.**

So a listener whose socket had quietly stopped — in any way that does not raise
`LoggedOutEv` — still got a green tick. This release has been about exactly that
failure, and it was sitting inside the command people run to look for it.

## Two sentences instead of one

The listener records its connection on every transition, and `check` reads it:

```
$ co whatsapp check
✓ whatsapp configured · listener pid 35771 · 0 unread · /Users/you/.co/inbox/whatsapp
✓ connected as 61410724095 since 2026-09-19T00:16:26Z
Next: co whatsapp listen
```

*Configured* is a claim about a machine. *Connected* is a claim about a socket,
and it now comes from the only thing that knows — with an account and a time,
so it can be disagreed with.

**A leftover record does not become a green tick.** A `connected` written by a
process that has since exited says what was true once; it is read only while the
pid that wrote it is the pid holding the lock. Otherwise the command says it
cannot tell — an answer that was not previously expressible, because the check
had no way to be uncertain.

## How it was found

Trying to confirm a live listener was healthy. Up an hour and forty minutes, no
log lines, so I reached for `session.db` having been written recently — which
turned out to be three hours old under a connection that was fine. It measures
traffic, not liveness. I had been holding a signal with one direction and
reading it in both, forty minutes after using it as proof of life in the same
session.

## Where 1.8.6 stands

**No open bug in the tracker is in this release's scope** — inbox, listen and
the mail CLIs, as #1555 cut it. Counted on 19 September there are 22 open bugs:
seven browser and remote-browser-host, two Workroom networking, one proxy, one
deploy, five `co ai` and agent core, two key handling, two Gmail/gws tooling,
and two release-metadata.

One of them deserves naming here rather than a category. **#1291** — `co ai`
exits 0 after printing "Task incomplete: Maximum iterations reached", so a
scheduler's `&&` runs the next step on work that did not finish — is the same
defect as this release's: a command reporting success for something that did
not happen. It is not in 1.8.6's scope and it is not fixed here, but it is the
same bug in a different command.

What is left before stable is not a defect list, it is runtime. Eleven of the
twelve problems found in 1.8.6 were found by somebody using it — the suite,
now 10,352 tests, reported none of them.

And runtime is measured per build, not per release line. The 1.8.6 listener has
been on a real linked account since 17 September and has taken 29 messages
there — but that is a5 and a6. **This build had been up fifteen minutes when
this note was written** (process start 00:16:24Z, connection record 00:16:26Z,
checked 00:31:39Z).

So the recommendation is runtime, not another checklist: let a7 sit on the real
account overnight before anyone decides about stable.
