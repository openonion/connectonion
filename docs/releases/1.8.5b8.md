# ConnectOnion 1.8.5b8 — beta

Beta, 14 September 2026. `co auth lark` begins on Lark.

Stable stays **1.8.4**. This is not Latest and needs an explicit pin or
`--pre`:

```bash
python -m pip install --pre connectonion==1.8.5b8
co --version
```

## Change

**`co auth lark` starts on the Lark accounts domain and says Lark throughout.**
Until now it printed an `open.feishu.cn` link. The SDK begins on Feishu
whichever brand you ask for and only moves to Lark after polling notices the
scanner's tenant is one — so it worked, and a Lark user asking for Lark read it
as the wrong product, because until they scanned, it was.

`brand` was already a parameter. It decided which env-file prefix to write and
nothing else. Four things beside it said Feishu unconditionally: the accounts
domain, the "Creating a … application" line, the remedy printed when a
registration comes back without a secret, and the reuse command offered from
lark-cli's config. The last two are commands a person is told to run.

Now `co auth lark` passes the Lark accounts domain, every sentence follows the
brand, and the reuse command takes its verb from the application's **recorded**
brand rather than the word typed — lark-cli wrote that brand at login, which is
better evidence than the command line just now.

`co auth feishu` still passes no domain, on purpose: the SDK's own
Feishu-to-Lark switch is what makes a Feishu link work for a Lark scanner, and a
test holds that in place.

## Reusing an application lark-cli already has

Asked directly this week: if lark-cli is already authenticated, can its
credentials be copied into `keys.env`?

Half of that already happens. `co auth lark` reads lark-cli's config and offers
the application ids it finds:

```
lark-cli has 2 application(s) configured on this machine:
  cli_aa00…  lark  (…)
To authorize one of those instead of creating a new one, and keep the
groups and permissions it already has:
  co auth lark --app-id cli_aa00…
```

The other half is refused on purpose. lark-cli keeps the secret in the macOS
keychain and its config holds only a reference to it. Copying a keychain entry
into a plaintext env file is a downgrade wearing the word "import" (#1497). One
scan with `--app-id` obtains the same credential with the platform's consent,
keeps the application's groups and permissions, and takes ten seconds.

Putting `co`'s own secrets in the OS keychain the way lark-cli does is #1497,
targeted 2.x — it changes where credentials live and has to hold on three
platforms, and this week added evidence that unattended paths (launchd, SSH,
`co deploy --to` servers) have no reachable keychain at all.

## Known limits

Unchanged: the no-loss-across-a-reconnect gate in #1462 has not passed, which is
why stable is still 1.8.4. A dedicated Lark test application for that run is
being created with the fixed command above; the run itself needs a human to
approve the application and post into a test group. A chat message can command
the agent and there is no sender allowlist until 1.9. A browser that exits on
its own takes the tab registry with it (#1513, targeted 1.8.6).
